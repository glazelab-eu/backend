# Sync

- `GET /api/sync` (`SyncService`, public like the listings) keeps clients' glaze and combination listings current with deltas; stock, favourites, clubs, member lists, buddies and buddy availability stay full fetches, club wishlists a page fetch (the log has no rows for them).
- The log is `change_log`: an identity `revision`, `changed_at`, `kind` (`GLAZE`/`COMBINATION`), `item_id` and one audience per row: `PUBLIC`, `CLUB` + club ID or `USER` + account ID (`ck_change_log_audience_id`). Rows hold IDs only and no foreign keys (a tombstone outlives its item).
- `ChangeRecorder` is the only writer. Every write that changes what a `GlazeView` or `CombinationView` shows (their `ImageView`s and `StepView`s included) calls it inside its transaction:
  - `glaze(id)` (every glaze is public); `combination(c)` (published: everyone; draft: its author only);
  - `picture(image)` (the audience of `ImageRecord.visibleTo` for the effective visibility, so a draft's photo names only its author: PUBLIC everyone, CLUB the club plus the uploader, PRIVATE the uploader), called before and after a visibility change, so the rows are the union of who saw it before or sees it after (a PUBLIC side reduces the item to one PUBLIC row; the PUBLIC ID move is an upsert of the parent).
  - Bulk statements record explicitly: `ImageRemovalService` every removed photo's parent; publication and deletion the variations (`CombinationRepository.variationsOf`: `basedOnId` shows only while the source is visible); account deletion its authored glazes and combinations, the glazes it corrected (`lastEditedBy`) and the parents of the shared photos it uploaded, before the anonymisation.
  - A refusal or rollback writes nothing; a no-op tag or barcode edit records nothing; recording outside a writing transaction throws.
- A new write operation needs a recording scenario or an `EXEMPT` reason in `SyncCoverageApiTest`, which runs every write operation of the OpenAPI document (and fails for a mapped write the document hides).
- Writes that bypass the recorder (a Flyway data migration, a manual SQL fix of view data, a restored database backup, whose revisions clients have already passed) bump `SyncService.FORMAT` (with the unchanged shape under the new number in `VIEW_SHAPES`), so every client loads in full. SQL admin grants need nothing (epoch).
- A glaze rename re-sends only the glaze: `StepView.manufacturer`/`name` mirror the glaze's current values and sync clients copy a corrected name into the steps that use it (topic "Contract"); a popular glaze would otherwise re-send thousands of combinations.
- Delivery: a row reaches a caller only if they are in its audience (their account, one of their clubs, or everyone). The delta renders the changed IDs through `LibraryViews` with the caller's viewer (the listing's visibility rules and per-viewer fields: `own`, `draft`, `stepsLocked`, `canDelete`, photo filtering, `basedOnId`).
  - A changed ID that does not render is a tombstone (`removed…Ids`) only when the item is gone (`CombinationRepository.existingAmong`): an existing item that does not render was never the caller's (glazes are public, publication is one-way, a draft is its author's), so a row logged for too wide an audience still never names someone else's draft. Anything that could hide a seen item, such as unpublishing, needs its own tombstone rule here.
  - A hidden photo and its ID never reach anyone outside the audience: photos travel only inside their parent's view, filtered per viewer.
  - A delta needs the same number of statements however many items changed (`SyncQueryApiTest`).
- Cursor `<revision>.<epoch ms>`: the newest revision in the answer's snapshot that the caller may receive (`ChangeLogRepository.topFor`, never below the previous cursor; the global newest would let anyone watch when others edit drafts or private photos) and the server time taken before it.
  - One `REPEATABLE_READ` read-only transaction holds the cursor, rows, views and the integrity counts (`visibleGlazes`/`visibleCombinations` = the caller's listing sizes after applying).
  - A delta answers rows after the revision plus rows written within `SyncService.OVERLAP` (2 minutes) before the time. The commit-order bound: a transaction commits within the overlap after its log insert, its last statement (`SyncOverlapApiTest`, on PostgreSQL `SyncConcurrencyApiTest`). Re-delivery is idempotent.
  - A full load takes a cursor first (the resync answer) and reads the listings after it, so nothing committed meanwhile is missed.
- A new enum value inside a stored view (image kind `IN_PROGRESS`) needs no bump while clients store and skip values they do not know (frontend "Pictures"): record the new shape under the current number in `VIEW_SHAPES`.
- So does a new nullable field whose null every stored view already means (`ImageView.focusX`/`focusY`: no stored photo had a focus, and a missing one is the centre).
- Resync answers (`SyncDtos.Resync`: lists empty, a fresh start cursor, the snapshot's counts for a paged load's progress): `CURSOR` (none, unreadable, beyond the newest revision or in the future), `FORMAT` (`SyncService.FORMAT` differs; bump it when a stored view's shape changes, `SyncCoverageApiTest.VIEW_SHAPES` fails until then), `EPOCH`, `EXPIRED` (cursor older than `RETENTION`, 30 days), `TOO_MANY` (more than `MAX_ITEMS` changed items; the row query stops at `MAX_ITEMS + 1`, so a fabricated old cursor costs one bounded query).
- Epoch (`SyncService.epoch`): a hash of the caller's account, clubs with roles and site-admin flag, derived per request, never stored (a stored counter would make a removal lock the removed member's row). It covers what changes the caller's views without a row per item: joining, leaving, removal, role changes and SQL admin grants. Any difference forces a full load on every device of that account.
- Retention: the daily `SyncService.purge` deletes rows older than retention plus overlap, always keeping the newest row.
- `GET /api/sync/combinations?after=&limit=` pages the caller's combination listing by ID (limit clamped to 1–1000) for a resumable first sync started from a sync cursor.
