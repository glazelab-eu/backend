# Tests

- HTTP tests are `controller/<Feature>ApiTest` on `support/ApiTestBase` (a running server; each `RestTestClient` is its own browser session with automatic CSRF; responses are read into the `*View` records).
- Shared helpers live in `ApiTestBase` (`signUp`/`user`, `register`, `login`, `siteAdmin`, `assertError`, `uploadTile`, `measured`, `jdbc`); add a helper there when a second test needs it, never a private copy.
- `ApiTestBase` and `AccountEmailApiTest` (GreenMail) run with rate limiting off; `security/RateLimitApiTest` uses tiny budgets and per-test client IPs via `X-Forwarded-For`.
- `ApiTypesTest` rejects entity or cyclic types in endpoint signatures. The OpenAPI drift check reads `../frontend/openapi.json` (tests reading `../frontend` skip when it is absent).
- `mvn test` runs four JVMs in parallel (`forkCount` in `pom.xml`; `-DforkCount=1` runs one), each with its own in-memory H2 shared by its test classes: use dynamic ports, never fixed ports or shared files, and assert on your own IDs.
  - Sync tests: also date earlier rows out of the overlap window (`SyncApiTest.settle`) before asserting that someone receives nothing.
  - Public catalogue tests: scope absence assertions to the test's author or IDs, never a generic title prefix across the whole listing.
- `storage/S3ImageStorageTest` and `controller/S3ImageApiTest` (the API on `GLAZELAB_STORAGE=s3`) run against the in-process fake `support/FakeS3`; `ApiTestBase.assertStored` checks both objects of a picture.
- `FreeTextApiTest` runs on PostgreSQL as `FreeTextPostgresApiTest` (NUL is storable on H2 only: compare registration answers byte for byte there). `PictureConnectionApiTest` runs on a pool of two (Flyway needs two at start) with a spied `ImageStorage` that blocks.
- `MigrationTest` runs on H2; `MigrationPostgresTest` runs the same tests on PostgreSQL, one database per test (see the PostgreSQL run below; run it before every release with a migration). New migration tests stay portable: generate UUIDs in Java or call `RANDOM_UUID()` (provided there), read columns and indexes through `columns`/`indexes`, constraints from `CONSTRAINTS` (PostgreSQL 18 lists NOT NULL constraints too).
- PostgreSQL lock-queue tests wait with `ApiTestBase.awaitWaitersBehindMe` inside the transaction holding the lock: it counts only sessions queued behind that transaction, never another class's waiters.
- `ServerMessagesContractTest` scans the main sources for answered messages (literals and string constants at the message sites it lists) and fails on one missing in `../frontend/src/lib/i18n/server-messages.ts`; a message assembled at run time is invisible to it.
- Optional runs against real servers (disposable ones only, never development or deployment data):
  - S3: `S3ImageStorageTest.RealServer` with `GLAZELAB_TEST_S3_ENDPOINT` (+ `_BUCKET`, `_ACCESS_KEY`, `_SECRET_KEY`, optional `_REGION`/`_PATH_STYLE`), for example against `chrislusf/seaweedfs server -s3` on a tmpfs.
  - PostgreSQL: `mvn -Dtest='MigrationPostgresTest,*ConcurrencyApiTest,*PostgresApiTest,ServerErrorDetailLogTest' -DforkCount=1 test` with `GLAZELAB_TEST_POSTGRES_URL` (a throw-away database, e.g. a `postgres:18-alpine` container; optional `_USER`/`_PASSWORD`, default postgres/empty) and `GLAZELAB_TEST_POSTGRES_IMAGES` (an isolated writable directory).
  - After removing a scratch migration, delete its copy under `target/classes/db/migration/` too: Maven keeps stale resources.
- Only with those env vars: `S3ImageStorageTest`'s `RealServer` tests, `CombinationConcurrencyApiTest` (real PostgreSQL lock queues; no orphan objects), `SyncConcurrencyApiTest` (`SyncOverlapApiTest` on PostgreSQL), `BuddyConcurrencyApiTest`, `BanConcurrencyApiTest` (its own image directory), `ReportConcurrencyApiTest`, `StockConcurrencyApiTest` (`StockJarApiTest` on PostgreSQL) and `AvatarConcurrencyApiTest` (its objects go to its own directory under `target/`, so `CombinationConcurrencyApiTest`'s exact object check of the shared directory holds).
- Profile picture tests upload `TestImages.unique()` (`ApiTestBase.avatar`) or seeds of their own (`AvatarModerationApiTest`): a site admin's removal blocks a picture for every later upload in the JVM's database, so tests never share a picture they may block (no admin ever removes the shared `PNG`).
- Ban tests (`BanApiTest`) block only addresses and pictures of their own accounts (`email(…)` addresses, `TestImages.unique()` pictures): a ban blocks for every later registration and upload in the JVM's database. A test that needs the hash of an address uses a real ban or `EmailBlocklist`'s bean, never a copy of the key.
- In tests `save` may merge assigned-UUID entities: use the returned instance.
- No servlet session may ever exist: `ApiTestBase.ServletSessions` (an `HttpSessionListener` in every `ApiTestBase` context) records each one with the stack that created it, and `ApiTestBase` fails the test during which it was created.
- Sessions (`security/LoginSessionApiTest`): backdate `login_session.renewed_at`/`created_at` with `jdbc` instead of waiting. `LoginSessionApiTest.secondApplication` starts a second application on `ApiTestBase`'s in-memory database (the restart and the Secure-cookie tests).
- A second application in a test takes its settings as command-line arguments: `SpringApplicationBuilder.properties` are defaults, which `application-dev.properties` overrides, so it would open (and migrate) the developer's `./data` H2 file.

## Schema

- The migration rules (new migration per change, named constraints, native `UUID` columns) are in `AGENTS.md` "Hard rules". Example of naming: `V6__magic_link_tokens.java`. ID fields are plain `UUID` fields, no `@JdbcTypeCode`.
- Addresses: every account is looked up by `app_user.email_key` (`EmailAddresses.key`: trimmed, `toLowerCase(ROOT)`, each code point through upper and back to lower case, so a long s or a dotless i meets the plain letter; unique `uq_app_user_email_key`, V37). Sign-in, registration, account mail, the pending purge and the sign-in delay use it; never compare `lower(email)` or `upper(email)` in a lookup. A raw `app_user` insert in a test sets `email_key`.
  - Not an expression index: H2 has none, and SQL `lower()` folds differently from Java (and only ASCII under the C locale). A changed `key` needs a migration that recomputes every key; V37 keeps its own frozen copy.
  - V37 stops (nothing changed, account IDs in the message, never addresses) when two accounts share a key. Operator pre-check before the release (PostgreSQL; `lower(upper(...))` approximates the Java fold, the migration's own check decides): `SELECT lower(upper(lower(trim(email)))) AS address, count(*), string_agg(id::text, ', ') FROM app_user GROUP BY 1 HAVING count(*) > 1;`. Resolve each group (keep one account), then start again.
- H2 binds `IN (...)` check constraints to the creating session: migration tests that insert after a partial Flyway run reuse one connection (`SingleConnectionDataSource`, see `MigrationTest`).
