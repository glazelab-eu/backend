# Security

- The hard rules (CORS, CSRF, filters only in the security chain, lookups by the principal's UUID, one constant per message) are in `AGENTS.md`.
- Security errors return JSON (429 included, with `Retry-After`).
- Error texts: `CurrentUser.SIGN_IN_REQUIRED` is the 401 text everywhere, filters included; only a failed form sign-in answers its own 401 text (`SecurityConfig`).
- Integrity failures answer by SQLState (`ApiErrorHandler.conflict`): unique 23505 is 409 `DUPLICATE`; a data exception (class 22) or check violation (23514, H2 23513) is 400 `INVALID_INPUT`; anything else (a foreign key 23503 hit by a concurrent delete) is 409 `CHANGED_MEANWHILE`.
- Free text: every text field of a request goes through `model/Text` (topic "Code rules"), so control characters answer 400 before any lookup or write; the 22-class mapping is only the backstop.
- Sign-in: an address with a control character is unknown without a lookup (`SecurityConfig.users`); the provider still hashes the password, and nothing logs a stack trace.
- Body size: `BodySizeFilter` (after `RateLimitFilter`, before CSRF) refuses a non-multipart body above `MAX_BYTES` (128 KB) with 413 `TOO_LARGE`, by `Content-Length` at once and for a chunked body once the bytes read pass it; Tomcat's form limit is the same. Multipart keeps the 12 MB multipart limit; `POST /api/reports` reads at most 32 KB itself. The proxies in front cap the same way (topic "Contract").
- Bean Validation fails fast (`config/ValidationConfig`), and every request list has a `@Size` bound, so an oversized list is refused before its elements are validated.
- Rate limiting: `RateLimitFilter` runs before CSRF and sign-in and trusts the proxy IP chain: the proxies overwrite `X-Forwarded-For` with the client address (topic "Contract"). Requests are classified by the decoded path Spring MVC matches, never the raw URI (`%6F` would dodge a budget). Budgets (`RateLimiter`; each `glazelab.rate-limit.<kind>.burst` then `.per-minute`):
  - AUTH and CONTACT: token buckets per IP.
  - The client key parses only text shaped like an IPv6 literal (`RateLimiter.clientKey`, zone dropped), so a remote address never becomes a DNS lookup; anything else keys on its raw text.
  - Sign-in delay per address (`SignInDelays`, `SignInDelayFilter` after CSRF, before the form sign-in; `glazelab.rate-limit.sign-in.*`, never scaled by `factor`, off with the limits): keyed by a hash of the address's lookup key (`EmailAddresses.key`, topic "Schema"; a long s counts for s), known or not, whichever IP tries.
    - Every attempt counts when it starts, so parallel attempts cannot pass while a password is hashed; a successful sign-in and every consumed account link (magic link, reset, verification) clear the count (`delays.reset`).
    - From the 5th counted attempt on, the next one waits 1 minute, doubling to at most 15 (429 `SignInDelays.DELAYED` with `Retry-After`, before any password is compared); the count is forgotten 24 hours after the last attempt.
    - Never a lockout: email links keep working while the address waits; a table full of delays in force lets new addresses through untracked rather than delaying them.
  - Tables (`BoundedTable`, `max-clients` entries each): an entry goes only once it holds nothing a fresh one would not (`RateLimiter.Client.quiet`: every bucket full again, no flag, no open count), never because newer keys arrived; a full table sweeps at most once a second. While the client table is full of clients that are not quiet, new clients share one overflow client; a full delay table first forgets counts below the threshold.
  - API and IMAGES: per IP + account when signed in, boosted by `signed-in-factor` (`RateLimiter.boosted`). Profile picture downloads (`GET`/`HEAD /api/avatars/**`) are in the IMAGES budget with its unknown-ID tarpit count.
  - Per IP + account and never boosted: TOKEN (buddy link preview and request, against token guessing: `glazelab.rate-limit.token`, 20 then 6/min); AVATAR (`POST /api/avatars`, each a full decode and encode: `glazelab.rate-limit.avatar`, 5 then 1/min); REPORTS (`POST /api/reports`: `glazelab.rate-limit.reports`, 6 then 2/min, the app's own pace); FEEDBACK (`POST /api/feedback`: `glazelab.rate-limit.feedback`, 5 then 0.1/min = 6 an hour; `Budget.perMinute` is a double for it). Refused uploads, batches and sends count too.
  - Never limited: `/api/health` and `GET /api/auth/clear-cache` (`kind` null: no server work, nothing reflected).
  - `Tarpit` decoys stay bounded: async non-blocking writes from one scheduler thread, a connection cap, a shared chunk, `no-store`.
  - A decoy replaces only a flagged client's unknown-picture answer (an IMAGES GET answering 404 or 400): never a JSON answer, never a picture that exists. `RateLimitFilter` holds the answer of a drawn request back to decide.
  - A 404 for a picture that exists but is hidden from the caller never counts as unknown (stale listings ask for those): the download calls `RateLimitFilter.hiddenPicture()` before its 404.
  - A refused second counts towards the flag only when the client asked again before the `Retry-After` of that budget ran out.
- Terms: `TermsFilter` (after `SessionVersionFilter`) answers 428 to writes outside `/api/auth/` while `accepted_terms_version` is NULL or not current; `POST /api/auth/terms` records version and server time; the first acceptance comes with the activation (topic "Registration"). Every exemption compares the decoded path Spring MVC matches (`TermsFilterTest`), never the raw URI. Two more routes pass the filter:
  - `DELETE /api/avatars/{id}` (exactly one segment): withdrawing one's own profile picture never needs new terms. `AvatarService.remove` answers 428 itself to anyone else's removal (site admins included); uploads, reports and the admin decisions stay behind the filter.
  - `PUT /api/account/diagnostics`: turning error reports off never needs new terms; `ReportService.choose` answers 428 itself to turning them on.
- Site admins (`app_user.site_admin`) are granted only with SQL (`UPDATE app_user SET site_admin = TRUE WHERE lower(email) = lower('…')`); no endpoint sets the flag. Check with `CurrentUser.siteAdmin` (401 guests, 403 others). A site admin can never be banned (topic "Bans").
- The source URL (`GLAZELAB_SOURCE_URL`) is the opposite of the operator contact: public in the sign-in options for everyone (topic "Licences").
- Operator contact: `GLAZELAB_OPERATOR_EMAIL` is public but only on request. `GET /api/auth/operator-contact` answers `OperatorContactView` `{email}` (404 `CONTACT_NOT_CONFIGURED` while unset, `Cache-Control: no-store`); never put it into the auth options or any listing. The filter classifies it as `RateLimiter.Kind.CONTACT` (`glazelab.rate-limit.contact`, 5 then 2/min, per IP only, never boosted, `RateLimiter.perAddress`), so a harvester is slow and the API budget untouched. Keep it separate from SMTP credentials.
- PostgreSQL's error detail (`Key (email)=(…) already exists`, also on foreign-key and check violations) reaches Hibernate's `SqlExceptionHelper` and every `PSQLException`/`DataIntegrityViolationException` message, so `application-prod.properties` sets `spring.datasource.hikari.data-source-properties.logServerErrorDetail=false` (the SQLState that `ApiErrorHandler.isUniqueViolation` reads stays).
  - It lives in the properties file, not the URL, so it holds for any `GLAZELAB_DB_URL`; a `logServerErrorDetail` parameter in an operator's URL would win: never put one there.
  - `ServerErrorDetailLogTest` (PostgreSQL-gated, loads `application-prod.properties`) fails without it.
- `application-prod.properties` also states the pool (10 connections, 30 s wait) and `options=-c lock_timeout=10s`: a lock wait past 10 s fails (an unhandled 500 with the ERROR line) instead of queueing; statements have no time limit, and Flyway runs under it (`MigrationPostgresTest`). An `options` parameter in the URL would win.
- Never log an exception message or value that can hold an address, token or password. `ApiErrorHandler` logs only unhandled failures (`log.error(…, ex)`, so keep their messages value-free) and never the 409 handler's exception.
